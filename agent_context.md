# Project summary and context
#10/11/26
This project is a web-based system for analysing areas at risk of land subsidence. Its core is the detection of subsidence bowls in InSAR/EGMS data using the methods supplied by my supervisor (circlet transform, Hough-based circle and ellipse detection), combined with land cover (CLC 2018), CBDG subsidence forecasts and flood-prone area data. Supporting analysis is done in ArcGIS Pro, while the final application is a web app.
The main objective of this thesis is to create and implement a system for analysing the area at risk of land subsidence. This idea is supposed to be achieved by conducting the analysis of land subsidence and combining its results with gathered geospatial data such as land use and land cover. Spatial data often contain detailed information about chosen area. A convenient visualisation of joined data is important in order to make the data easier to read useful details. Therefore, implementation of the system is intended to help understand the data needed to analyse the identified areas at risk of land subsidence through its visualisation in a form of a web application which allows an interactive presentation of displacements, adding themed layers and generating basic reports. This paper focuses on obtaining and processing radar imagery to determine a map of displacements and integrating the results with land use and land cover data using created system as well as the analysis and visualisation of the outcome based on chosen area of interest.

 This paper is meant to discuss the course of creating the system using chosen GIS system and programming environment using geospatial data

## Stack and key decisions

All data lives in PostgreSQL/PostGIS in EPSG:3035 (ETRS89-LAEA), which is the native CRS of EGMS, so area and distance calculations stay in metres. The web map itself runs in Web Mercator with an OSM base layer, and the API reprojects geometries to EPSG:4326 in SQL (`ST_Transform`) only on the copy sent to the browser. The backend is Python and Flask, configured through `.env` and `config.py`, and the same Flask app also serves the frontend, so one command starts the whole system. The frontend uses plain Leaflet with vanilla JS (react-leaflet was dropped because of time constraints). Layers are described by a catalogue in the backend (`LAYERS`), and the frontend builds the layer control from the `/api/layers` endpoint, so a new layer is a single configuration entry. Rasters (EGMS, hillshade) are loaded client-side from GeoTIFF files with georaster-layer-for-leaflet and proj4, so a dedicated raster blueprint in the backend is no longer planned. All image processing for bowl detection is done in MATLAB, working directly on the GeoTIFF exported from ArcGIS, and the binarisation step is done in ArcGIS Pro with a threshold of -15 mm/year on the vertical velocity raster (class 2 means intensive subsidence, class 1 means everything else).

## What is done

On the data side, I have the EGMS L3 100 km vertical product (2019-2023), plus a separate horizontal displacement set (2020-2024). In PostGIS, EGMS is split into point tables (`egms_points`, `egms_points_stats`, `egms_horizontal`) and a long-format `egms_timeseries` table. I have also prepared CLC 2018 clipped to the study area (loaded into PostGIS with 2D geometries and the correct layer), the CBDG forecast and flood-prone area layers, and a DTM with hillshade and slope.

The detection pipeline in MATLAB is finished: it builds a density map of intensive-subsidence pixels, applies the circlet transform as a shape filter and derives bowl masks with `imreconstruct`. The detected contours have been exported to a shapefile with ID and Area_m2 attributes, georeferenced from the raster.

The application works end to end. The Flask backend exposes a layer catalogue (`/api/layers`) and a GeoJSON endpoint per layer (`/api/layers/<name>`). Static layers (CLC, CBDG forecast, flood areas) are loaded once, when the layer is ticked in the control. CLC is styled by land cover code with the legend colour map, and the EGMS points are restricted to the area of interest polygon and loaded by map view (bbox and zoom) with a velocity range filter. Unticking a layer clears its data so that it reloads cleanly next time. Importing paths, `config.py` and the loader script are sorted out, and the removed raster blueprint no longer appears anywhere in the code.

## What remains

The detected bowl contours still have to be loaded into a `risk_areas` table in PostGIS (CRS 3035, 2D geometry, spatial index), and I need to check that they land in the right place on the map. After that, the layer gets a catalogue entry and a style on the frontend. The two main next steps are generating reports, which is the priority, and adding the remaining layers from the database to the system. The time series chart for a clicked EGMS point has been set aside for now (the `egms_timeseries` table exists, but there is no endpoint yet). Later stages that are not being prioritised at the moment are the conditional SNAP interferogram processing, ranking of at-risk areas, analysis of the study area and system testing.
